# Taste
- Writes and expects replies in Vietnamese (casual, unpunctuated, mixed loanwords). Keep chat replies, code comments, and the README in Vietnamese unless asked otherwise. Git commit messages are the exception: those go in English with a structured body (summary, per-module breakdown, business rules, bugs found, how it was verified, `Co-Authored-By` trailer). Confidence: 0.85
- Gives short, high-level briefs ("make a clothing site for men and women, make it pretty, set it up") and expects the agent to fill in the architecture and make routine decisions rather than being asked about every choice. Mid-task the nudge is even shorter — "tiếp tục đi aj" — which means "keep going on your own", not "tell me what to do next". Drive the task to a finished, verified state without interim check-ins. Confidence: 0.85
- Full-stack default is NestJS (backend) + Next.js / React (frontend), TypeScript throughout. Confidence: 0.85
- Builds UI from a component registry — explicitly asked for ReUI, which is shadcn-compatible. Reach for shadcn-style registries when choosing UI primitives. Confidence: 0.8
- Cares about visual quality, not just function ("làm sao cho đẹp là được"). Budget real effort for polish and for looking at the rendered result. Reviewing the rendered output is not optional: screenshot the pages, read the screenshots back, and treat what you see as a source of defects — an untranslated raw enum leaking into a select trigger ("all" instead of "Mọi giới tính"), stray debug rows, bad spacing all got caught this way, not by the test suite. Confidence: 0.85
- Wants backend and frontend clearly separated, stated as being for their own maintainability ("để tôi dễ maintain"). Prefer a monorepo with distinct `backend/` and `frontend/` apps over mixing concerns. Confidence: 0.85
- Strongly wants dependencies on the newest possible versions — challenged the agent for using Prisma 7 ("ủa sao ko dùng prisma 8 mới nhất chuyển sang dùng các thứ mới nhất nhé chứ ok được dùng các version cũ đâu"). Run `pnpm outdated` / `npm view <pkg> dist-tags` proactively and upgrade rather than defaulting to conservative pins. Confidence: 0.9
- When offered "keep stable" vs "upgrade to new major/RC", picks the new major (chose Prisma 8 RC and TypeScript 7 over the recommended stable versions). Default to proposing the bleeding-edge option as viable. Confidence: 0.75
- Expects the agent to explain a version decision with concrete evidence (npm dist-tags, peer deps, whether packages are actually published) rather than deferring to stale knowledge about what "latest" is. Confidence: 0.7
- Does not want to be asked which version to install — "cứ cài cả cho là latest đừng chỉ định phiên bản", and pushed back on an ask_user_question with "tôi đã hỏi quá nhiều". Use `@latest` or a range like `typescript@^6` instead of exact pins, try the upgrade, diagnose blockers yourself, and report back. Confidence: 0.9
- Secrets hygiene matters to them indirectly: `.env` files with `JWT_SECRET` / DB credentials must stay out of git while `.env.example` is committed, and the agent should say what must be recreated after a fresh clone. Confidence: 0.6
- When a package genuinely cannot go to latest, expects the exception to be recorded with its technical reason in the README (and commit message) instead of being silently dropped — the pinned versions should be traceable and easy to lift later. Confidence: 0.75
- Asks the agent to set the project up end to end ("hãy cài setup project giúp tôi") — a scaffolded project with dependencies installed and building/running is the deliverable, not snippets to paste. Confidence: 0.8
- Sends copy-pasted boilerplate shell snippets (e.g. GitHub "quick setup" scripts) as shorthand for a goal, not as literal instructions. Expect the agent to reconcile them with the real repo state, drop destructive/incorrect steps, and say what it actually did instead of running them verbatim. Confidence: 0.75
- GitHub habits: SSH remotes (`git@github.com:<user>/<repo>.git`), `main` as the branch name (never `master`), and is happy for the agent to make repo-level decisions (branch rename, adding `origin`) without asking. Confirms pushes by listing the resulting commit SHAs. Confidence: 0.7
- Wants product imagery on their own managed CDN rather than hotlinked stock photos. Picked Cloudinary and asked to migrate the catalog off Unsplash URLs ("chuyển sang dùng đẩy ảnh lên đây"). Assume self-hosted/managed asset storage is the target whenever images are involved. Confidence: 0.65
- Hands over credentials and settings as a screenshot of the provider's dashboard instead of typing them. Expect secrets to arrive as compressed images: read them out, verify them against the provider's live API, and if rejected (e.g. `unknown_api_key`) ask for the exact value or leave a clearly marked placeholder in `.env` rather than guessing digit variants. Confidence: 0.7
- Prefers managed cloud services over local containers for infrastructure — told the agent to switch PostgreSQL to Aiven Cloud and stop using the local one. When given a hosted option, default to a managed provider; keep local Docker documented only as an offline fallback. Managed services imply their constraints too (TLS/`sslmode=require`, connection-pool caps for free tiers). Confidence: 0.7
- Dislikes catch-all files that grow with the feature set, and asks for them to be split by domain as the project scales ("sau còn nhiều api nữa mà tất cả sao để chung vào 1 file"). Refactor into per-domain modules plus a barrel re-export so call sites stay short and adding an endpoint only touches one file — don't wait to be asked. Confidence: 0.85
- On architectural choices, defers to the prevailing industry convention rather than a personal pick: "thực tế người hay dùng cái nào thì mình dùng cái đó". Pick the mainstream pattern, say in one line why it's the standard, and rule out the rejected alternative (e.g. why API calls don't belong in `app/` under App Router) so the choice is auditable. Confidence: 0.8
- Wants types isolated from code, not just grouped by domain: "làm folder riêng hay gì đó cho types đi chứ sao lại để chung như này". Keep `lib/api/` for call code only, `lib/types/` for models only, constants like `API_URL` in their own `config.ts`. A domain folder holding `x.ts` next to `x.types.ts` reads as noise to them. Imports should make the distinction visible (`from '@/lib/api'` vs `import type { X } from '@/lib/types'`). Confidence: 0.85
- Privileged surfaces must be obvious from structure alone, not from reading the code: "viết như kia thì chả biết api nào là của admin". Expect a dedicated `admin/` module and folder on both sides, an `/api/admin/*` route prefix, a general `RolesGuard(allowedRoles)` rather than an admin-specific guard, and `adminApi` deliberately left out of the public barrel so call sites must import it explicitly. Confidence: 0.85
- When they flag a structural problem, expect a full sweep of the stack, not a local patch: "cả be và fe check lại cấu trúc nhé". Survey the whole directory tree of every affected app first, then fix all of it, and grep for stale imports/paths afterwards rather than trusting the compiler. Trigger cases so far: mixed file types, mixed naming, mixed auth coverage. Audit every controller/route decorator in one pass rather than fixing the file currently open. Confidence: 0.8
- Security coverage must be uniform across every module, and the mixed state is itself the bug: "cập nhật để tất cả các module đầy đủ auth đi cái có cái không thế". When offered the two shapes, chose default-secure: register the JWT guard globally via `APP_GUARD` and let public routes opt out with a `@Public()` decorator, so a new controller is protected by construction instead of by remembering `@UseGuards`. Prefer this over opt-in guards plus documentation, and strip the now-redundant explicit guard lines from controllers. Keep a single `decorators/` folder for `@Public` / `@CurrentUser` rather than scattering them under `common/`. Confidence: 0.8
- When they ask for something "đầy đủ" (complete) — "hãy làm đầy đủ tất cả các crud đầy đủ các module cho admin đi ạ" — they mean the whole surface area in one pass, not the resource that happens to be easiest. Enumerate the full list up front (categories, products, orders, users, stats), ship every one, and prove each with tests; a half-built admin reads as unfinished to them. Confidence: 0.75
- Verification is expected to be real, and browser-level. A green typecheck/lint is not enough: stand up the dev server and drive the actual flows with a throwaway Playwright script, then delete the script. Assert against the API as well as the DOM — after each mutation, confirm the screen and `GET /admin/*` agree — and quote a summary like "19/19 bước" in the final report. A failing UI test is a bug in the app to be root-caused, not a selector to keep loosening. Confidence: 0.8
- Diagnosing an E2E failure: write a small one-off Playwright/Node probe that dumps the real DOM (button counts, `innerHTML`, `data-slot` attributes) or hits the API with `curl`, instead of speculating about selector indexes. Guessed indexes were wrong repeatedly; the probe found the answer immediately. Likewise an unexpected raw value (`'all'` in a trigger) or a 401 usually means a parsing/serialization detail, not a broken app. Confidence: 0.75
- E2E tests must be hermetic: suffix every created record with `Date.now()`, and delete everything matching that prefix (products, categories, users) from the database afterwards. Before committing, check row counts against the seed's original state (e.g. 9 products / 9 categories / 144 variants) and confirm the real catalog survived — a leftover `TestBrand` product prompted "còn 1 sản phẩm test. Dọn lại cẩn thận." Scratch cleanup includes the test script, screenshots, and any test rows, not just the file. Confidence: 0.8
- Rerun the full suite after any late fix, and rerun both backend and frontend suites before committing. Lint/typecheck passing is not evidence that an earlier refactor didn't regress behavior. Confidence: 0.8
- Business rules belong on the server, not the client, and the report is expected to list them explicitly ("server tự chặn, không tin client"): soft-delete products that appear in orders, forbid deleting order-referenced variants, expose legal order status transitions via a `/transitions` endpoint the UI consumes, return stock in the same transaction on cancel, and self/last-admin protection. Enforce in the backend and surface them in the README. Confidence: 0.75
- Documentation gets the same rigor as the code: README gets a full endpoint table (method/path/description), the business-rule list, updated directory trees for both `backend/` and `frontend/`, and a scripts-table row for the test suite. Flag a live admin password at the end ("nhớ đổi hoặc xoá trước khi lên production"). Confidence: 0.75
- Final report format: a short Vietnamese summary of what shipped, grouped by area (backend routes table, business rules, frontend pages), the real bugs found and fixed while wiring it up, and a verification list with counts. Lead with what is done, not a narrative of the process. Confidence: 0.7
